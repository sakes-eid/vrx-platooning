## Q3. Identify the main ROS 2 concepts used in the project: node, topic, message, publisher and subscriber.

The project uses several ROS 2 nodes that exchange information through topics.

A simplified R1 architecture is:

    VRX sensors
        |
        v
    multi_vehicle_state
        |
        v
    /r1/vehicle_state
        |
        +------------------------+
        |                        |
        v                        v
    stress_course_planner   leader_stress_controller
        |                        |
        | speed / lookahead      |
        +----------------------->|
                                 |
                                 v
                        WAM-V thruster commands

A node performs a specific function.

A publisher sends information to a ROS 2 topic, while a subscriber receives information from a topic.

ROS messages define the structure of the information exchanged between nodes.

ROS parameters are also used to configure controller gains, planner limits and experiment settings without changing the control logic.

## Q5. Identify the topics used to command the robot and obtain its state.

The WAM-V is actuated using its left and right thrusters.

Important command topics include:

    /wamv/thrusters/left/thrust
    /wamv/thrusters/right/thrust

The thruster steering angles are kept fixed straight.

Therefore, yaw motion is produced using differential thrust:

    T_left != T_right

The vehicle state is derived primarily from simulated GPS and IMU measurements.

The project state-estimation layer publishes the processed R1 state on:

    /r1/vehicle_state

The state includes the position, heading and velocity information required by the planner and controller.

The navigation calculations are performed in the:

    world_ned

frame.

## Q6. Manually command the robot and verify its motion.

During the initial VRX experiments, the WAM-V thruster interfaces were tested manually.

Forward motion was obtained by applying approximately equal thrust to both thrusters.

Turning was obtained by applying different values to the left and right thrusters.

These tests confirmed that the WAM-V could be controlled using differential thrust while keeping the thruster steering angles fixed.

# Part 2 — Robot Modeling and Control

## Q7. Implement the robot model in the simulation environment.

The project uses the existing WAM-V dynamic model supplied by the VRX simulation environment.

The controller therefore operates on the simulated physical response of the WAM-V rather than replacing it with a purely kinematic robot.

For the trajectory-tracking problem, the vehicle state is considered in the horizontal plane:

    eta = [x, y, psi]^T

where:

    x   = North position
    y   = East position
    psi = yaw / heading

GPS and IMU measurements are transformed into this local navigation representation and published to the rest of the ROS 2 architecture.

---

## Q8. Identify the robot inputs and outputs.

The main control inputs are:

    Left thruster force
    Right thruster force

The thruster azimuth angles remain fixed at zero.

Longitudinal motion is mainly generated by the common component of the two thrust commands.

Yaw motion is generated by their difference.

The main outputs used for control are:

    x position
    y position
    heading psi
    longitudinal velocity
    lateral velocity
    vehicle speed

These quantities are obtained from the simulation sensors and processed by the state-estimation node.

---

## Q9. Define a reference trajectory.

The planner generates the reference trajectory in the `world_ned` coordinate frame.

Straight and curved trajectories were implemented during development.

A more demanding stress trajectory was then developed for final controller tuning.

The stress course contains:

    a long straight section
    a 90-degree tight turn
    180-degree turns
    directly connected turns
    a short connector
    coverage-style lanes
    a tight hairpin
    a wider opposite hairpin
    a final straight

This trajectory was intentionally made more difficult than a simple line or circle so that the controller could be evaluated under strong changes in curvature and direction.

---

## Q10. Select a suitable trajectory tracking control method.

A PID-based trajectory-tracking architecture was selected.

The R1 controller contains separate PID control functions for:

    heading control
    forward-speed control
    terminal braking

The heading controller produces differential thrust.

The speed controller modifies the common forward-thrust component.

The braking controller is used near the final target.

The controller is supported by a trajectory planner that computes:

    curvature-aware speed limits
    lookahead distance
    upcoming-turn information
    chronological path progress

---

## Q11. Briefly justify the selected method based on the literature.

A PID-based architecture was selected because heading and speed control are established feedback-control problems for marine craft and unmanned surface vehicles.

Fossen describes course and heading autopilot design as a fundamental marine-control problem applicable to surface craft and USVs. This provides a theoretical basis for separating the WAM-V control problem into guidance and heading-control functions.

Gutiérrez et al. experimentally developed a USV control system using separate PID controllers for speed and heading. This is particularly close to the structure used in this project, where the longitudinal motion and yaw response are regulated independently.

The final R1 implementation also separates high-level guidance from low-level control. The planner determines the reference path, permitted speed and lookahead, while the PID controller converts these references into actuator commands. Wu et al. use a comparable hierarchical concept in which a guidance system operates above a PID-based controller regulating USV speed and yaw.

A fixed lookahead was not retained for the final planner. Instead, lookahead is adapted according to operating conditions and upcoming path curvature. Wan et al. demonstrate that USV path-following performance can benefit from adapting lookahead according to vehicle speed and tracking error. Their low-level controller is different from the PID controller used here, but the work supports the general principle of adaptive rather than constant lookahead.

The selected solution therefore combines a computationally simple and interpretable PID controller with a separate trajectory-guidance layer. This architecture was suitable for ROS 2 implementation, systematic simulation tuning and later extension to a leader-follower platoon.

### References

1. Fossen, T. I. (2021). *Autopilot Models for Course and Heading Control*. In *Handbook of Marine Craft Hydrodynamics and Motion Control*, 2nd ed. Wiley. DOI: 10.1002/9781119575016.ch7.

2. Gutiérrez, C., Yacub, B., Sierra, E., Sánchez, S., & Contreras, J. *Speed and Heading Control System for an Unmanned Surface Vehicle - USV*. Ship Science & Technology. DOI: 10.25043/19098642.231.

3. Wu, N., Fan, Y., Wang, R., Wang, M., Wu, C., & Wang, Y. (2025). *Development and field testing of an unmanned surface vehicle system for guidance control and target tracking*. Ocean Engineering, 316, 119924. DOI: 10.1016/j.oceaneng.2024.119924.

4. Wan, L., Su, Y., Zhang, H., Shi, B., & AbouOmar, M. S. (2020). *An improved integral light-of-sight guidance law for path following of unmanned surface vehicles*. Ocean Engineering, 205, 107302. DOI: 10.1016/j.oceaneng.2020.107302.

# Part 3 — Trajectory Tracking with ROS 2

## Q14. Implement the trajectory tracking node.

Trajectory tracking is implemented using two cooperating nodes rather than a single monolithic node.

The planner is:

    stress_course_planner.py

    leader_stress_controller.py

Separating planning from low-level control also makes the architecture easier to extend later for R2 and R3.

## Q17. Compute the tracking error.

The implemented monitoring system computes several tracking errors continuously during the simulation:

    cross-track error
    heading error
    speed error

The principal geometric tracking metric used during development is the cross-track error. It measures the signed lateral deviation of the WAM-V from the reference trajectory and was used directly during controller optimization.

For the final visible R1 validation, the absolute cross-track-error statistics were:

    Mean absolute error = 0.326 m
    RMSE                = 0.409 m
    95th percentile     = 0.683 m
    Maximum error       = 0.980 m

The heading-error RMSE was:

    2.56 degrees

The project specification additionally defines the position error as:

    ep = sqrt((x - xd)^2 + (y - yd)^2)

The current final CSV logger stores the measured position `(x, y)` and the cross-track error, but it does not store the corresponding desired point `(xd, yd)` explicitly.

Therefore, the existing dataset should not be presented as if the exact PDF-defined `ep(t)` had been independently reconstructed.

For the final report, the plotting/logger stage should additionally store or reconstruct the desired reference point `(xd, yd)` and calculate:

    ep(t) = sqrt((x(t) - xd(t))^2 + (y(t) - yd(t))^2)

This is a remaining report-data task rather than a controller-design problem. The implemented cross-track error already provides the principal path-tracking metric used for controller evaluation.

## Q22. Use the leader information by the follower.

R2 subscribes to R1 state and uses it in two distinct ways.

### Longitudinal formation information

The predecessor trajectory is stored as an unsmoothed breadcrumb history.

The follower's longitudinal progress is projected continuously onto that raw history.

The V2.2 path-gap signal represents the approximate bumper-to-bumper separation along the travelled path:

    path_gap
      = predecessor path progress
      - follower path progress
      - predecessor rear extent
      - follower front extent

This signal is used by the distance PID.

### Lateral guidance information

The same breadcrumb history is smoothed into a local curve.

The smoothed path is used only for heading / cross-track guidance.

This separation prevents path smoothing from corrupting the longitudinal spacing measurement.

### Safety information

Exact oriented WAM-V rectangles are used to calculate minimum physical hull clearance.

This physical clearance is not used as the normal 5 m formation-control variable. It is reserved for:

    collision warning
    collision avoidance
    minimum-clearance reporting

## Q23. Develop the follower controller.

The current R2 controller contains four main functions:

    gap / distance PID
    heading PID + cross-track guidance
    speed PID
    terminal braking PID

The normal FOLLOW speed command is based on:

    predecessor speed
        +
    distance-PID correction

During larger initial separation, a CATCHUP mode raises the requested follower speed.

The controller also uses proactive historical speed information from the predecessor path to reduce speed before previously observed slow sections.

The current tuned R2 configuration is stored in:

    platoon_control/config/r2_follower_v22_tuned.yaml

The adaptive follower tuner uses the hierarchy:

    GAP -> HEADING / GUIDANCE -> SPEED -> BRAKING

A stage locks once its acceptance threshold is reached. Later accepted changes continue to monitor locked stages and reopen them if they drift outside threshold.

The 36-trial study exhausted its trial budget with:

    GAP     = LOCKED
    HEADING = OPEN
    SPEED   = OPEN
    BRAKE   = OPEN

The selected final trial is therefore the best current validated R2 baseline, not a claim that every optimizer gate was reached.

### Important reporting distinction

The project PDF defines:

    d12 = sqrt((x2 - x1)^2 + (y2 - y1)^2)

as the formal inter-robot distance.

The present controller's primary formation variable is instead the along-path bumper gap because this behaves more consistently through tight turns and matches the physical leader-follower interpretation used during development.

Therefore the final report should show both:

    1. the V2.2 along-path bumper gap used by the controller;
    2. the PDF-defined Euclidean d12(t) for direct compliance with Q24.

The current V2.2 results demonstrate convergence of the implemented formation variable to approximately 5 m with no subsequent loss of formation. The final PDF-defined d12 plot should still be generated explicitly before submission.
